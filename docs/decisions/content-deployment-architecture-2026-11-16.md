# 複数プロジェクトの公開・デプロイ責務に関する設計判断（2026-11-16）

## 決定したこと

1. XO-Code BustersがVPSの公開基盤（Caddy、公開URLの割当、共通デプロイ機構と運用手順）を管理する。講座・RPGなどの各リポジトリは、自身のソース、公開対象ディレクトリ、公開形式の宣言を管理する。
2. XO側は講座固有の内部ディレクトリ構造をハードコードせず、各リポジトリの `deploy.json` を共通インターフェースとして読み取り、公開処理を実行する。
3. 今回のプレゼン工房の講座は静的ファイルのみを公開する。今後も静的ファイルを基本とするが、動的アプリなどが必要になれば別途設計判断を行う。
4. 静的公開では、GitHubからVPSへクローン・更新したリポジトリ内の公開専用ディレクトリをWebサーバーが直接参照する。必要ファイルを別の公開用ディレクトリへコピーする方式は目標構成として採用しない。
5. 公開用ディレクトリの外にあるソース・設定・制作資料はWeb公開対象にしない。各リポジトリは公開内容を明示する。
6. Caddyなどの基盤設定はXO側のGitHubで管理し、稼働中のVPSへの適用はGit更新とは別の操作として扱う。公開URL・ドメイン、VPS上のGitクローン配置先、URL衝突防止はXO側が一元管理する。各講座の `deploy.json` に公開URLは記載しない。

## 公開定義の基本仕様（確定した責務分担）

各講座・RPGのリポジトリルートに `deploy.json` を配置する。静的公開の基本形は次のとおり。

```json
{
  "schemaVersion": 1,
  "publish": {
    "type": "static",
    "directory": "public"
  }
}
```

- `schemaVersion`：公開定義のバージョン。初期値は `1`。
- `publish.type`：公開形式。当面は `static` のみ。
- `publish.directory`：リポジトリルートからの相対ディレクトリ。例の `public` は標準的な候補であり、各リポジトリの実際の配置は個別に確認する。
- `deploy.json` は公開URLやVPS上の絶対パスを指定しない。公開URLの割当と物理配置先の管理はXO側が行う。
- ディレクトリの実在確認、リポジトリ外へのパス逸脱防止、公開URLの重複検出は共通処理側で扱う。
- 公開ベースURLに依存するHTML内の絶対パスについては、相対パスの利用を基本とし、必要に応じて後続仕様で扱う。

JSON Schemaの詳細な制約とXO側のURL割当設定ファイルの基本形式は2026-11-17に確定済み（次節参照）。このJSONは合意した最小構成を示すもので、現時点では読み取り処理は未実装。

## 静的公開インターフェースの詳細仕様（2026-11-17確定）

講座側はリポジトリルートの `deploy.json` に `schemaVersion: 1`、`publish.type: "static"`、`publish.directory` を必須で指定する。未定義プロパティは許容しない。JSON Schemaの正本は [deploy.schema.json](../../deploy/schemas/deploy.schema.json)。

- `publish.directory` はリポジトリルート内の相対パスであり、絶対パス・空文字・`.`・`..` セグメントを禁止する。実装時は実在と実体パスを確認し、シンボリックリンク経由を含めリポジトリ外を参照しないことを保証する。
- JSON構文不正、スキーマ不適合、対象ディレクトリ不存在、実体パスの領域外逸脱はデプロイ中止とする。既存の稼働設定は変更しない。
- `schemaVersion` は整数1のみを受理し、未対応バージョンは停止する。

XO側は [projects.json](../../deploy/projects.json) に公開先を定義する。基本構造は `schemaVersion: 1` と `projects` 配列。各要素に `repository`（GitHub owner/name）、`host`（ドメイン）、`path`（先頭と末尾がスラッシュのURLパス）を指定する。講座側の `deploy.json` にはURL・ポート・VPS絶対パスを持たせない。

- `repository` をXO側の管理対象として解決し、実際のクローン先はXO側の配置規則で決定する。GitHubリポジトリの任意文字列をシェルコマンドとして実行しない。
- `host` と `path` の組が重複する定義は不正とする。親子パスなどルーティングが重なる場合も衝突の有無を検証してから適用する。
- `projects.json` のスキーマは [projects.schema.json](../../deploy/schemas/projects.schema.json) を正本とする。現在の [projects.json](../../deploy/projects.json) は空配列の初期定義であり、既存公開サイトの割当を置き換えない。
- Caddyの生成・統合・適用手順、権限、URLパス接頭辞の扱い、起動方式・異常時復旧は後続工程で設計する。稼働中のCaddyfileを自動上書きしない。
- Node.js（Express）とPHPの公開形式は将来拡張候補であり、今回のスキーマでは未対応。実行方式・プロセス分離・ポートやPHP-FPMの割当を決定してから、バージョン管理された仕様として追加する。

### Node.js（Express）を利用する講座

講座リポジトリ側は実行ディレクトリと起動エントリポイントを宣言し、XO側がプロセス管理・ポート割当・Caddyリバースプロキシを担当する想定。

```json
{
  "schemaVersion": 1,
  "publish": {
    "type": "node",
    "workingDirectory": "server",
    "entryPoint": "app.js"
  }
}
```

- `workingDirectory` と `entryPoint` はリポジトリ内の相対位置を表す想定。
- 講座側の `deploy.json` には公開URL、VPS絶対パス、固定ポートを記載しない。XO側がポートを割り当て、`PORT` 等の環境変数でアプリへ通知する案。
- CaddyはXO側が管理する公開URLから当該Node.jsプロセスへリバースプロキシする案。
- 起動コマンドを文字列として受け取る案（例：`startCommand: "node app.js"`）も検討したが、任意コマンド実行の扱いが必要になるため、現時点では `entryPoint` 方式を優先候補とする。
- プロセスの分離、systemd等の起動・停止、Node.jsバージョン、依存関係インストール、環境変数・秘密情報、ヘルスチェック、障害復旧、サブパス配信時のベースパスは未決定。

### PHPを利用する講座

PHP-FPMとCaddyをXO側が管理し、講座側は公開ディレクトリと入口となるPHPファイルを宣言する想定。

```json
{
  "schemaVersion": 1,
  "publish": {
    "type": "php",
    "directory": "public",
    "index": "index.php"
  }
}
```

- `directory` はリポジトリ内の公開専用ディレクトリ、`index` はその中の入口ファイルを指す想定。
- PHP-FPMのソケット・プール・実行ユーザー・PHPバージョン・ファイル権限・Caddy設定・公開URLはXO側が管理する案。講座側のJSONにVPS固有の設定を持たせない。
- 非公開ソースや設定ファイルをWeb配信しない。PHPの実行対象と静的ファイルの公開範囲を明確に分離する必要がある。
- PHP-FPMの分離単位、依存ライブラリ、秘密情報、URL書換え、サブパス運用、アクセス制御、障害時の扱いは未決定。

### 共通方針と将来の判断事項

- 静的・Node.js・PHPのいずれも、講座側は自身の公開形式・必要な相対パスを宣言し、XO側はドメイン・公開URL・VPS配置・実行基盤を管理する。
- `publish.type` によって公開方式を分岐させる構想だが、動的方式を実装する前にスキーマの拡張方法・バージョン互換性・運用上の隔離とセキュリティを設計判断する。
- ここに例示したフィールド名や実行方式は変更可能。**現時点で想定している選択肢として記録し、将来の検討で「想定外」と扱わないためのメモ**とする。対応を保証するものではない。

## 判断理由

- 講座が増えてもXO側に講座別のデプロイ実装を増やさずに済むようにするため。
- 公開対象と非公開対象を各リポジトリで明確に分離するため。
- GitHubを正本として、公開内容の更新を単純にし、コピー先との二重管理を避けるため。
- コンテンツの責務と公開基盤の責務を分離するため。
