# 複数プロジェクトの公開・デプロイ責務に関する設計判断（2026-11-16）

## 決定したこと

1. XO-Code BustersがVPSの公開基盤（Caddy、公開URLの割当、共通デプロイ機構と運用手順）を管理する。講座・RPGなどの各リポジトリは、自身のソース、公開対象ディレクトリ、公開形式の宣言を管理する。
2. XO側は講座固有の内部ディレクトリ構造をハードコードせず、各リポジトリの `deploy.json` を共通インターフェースとして読み取り、公開処理を実行する。
3. 今回のプレゼン工房の講座は静的ファイルのみを公開する。今後も静的ファイルを基本とするが、動的アプリなどが必要になれば別途設計判断を行う。
4. 静的公開では、GitHubからVPSへクローン・更新したリポジトリ内の公開専用ディレクトリをWebサーバーが直接参照する。必要ファイルを別の公開用ディレクトリへコピーする方式は目標構成として採用しない。
5. 公開用ディレクトリの外にあるソース・設定・制作資料はWeb公開対象にしない。各リポジトリは公開内容を明示する。
6. Caddyなどの基盤設定はXO側のGitHubで管理し、稼働中のVPSへの適用はGit更新とは別の操作として扱う。公開URL・ドメイン、VPS上のGitクローン配置先、URL衝突防止はXO側が一元管理する。各講座の `deploy.json` に公開URLは記載しない。

## 公開定義の基本仕様（確定した責務分担）

各講座・RPGのリポジトリルートに `deploy.json` を配置する。静的公開の基本形は次のとおり。

```json
{
  "schemaVersion": 1,
  "publish": {
    "type": "static",
    "directory": "public"
  }
}
```

- `schemaVersion`：公開定義のバージョン。初期値は `1`。
- `publish.type`：公開形式。当面は `static` のみ。
- `publish.directory`：リポジトリルートからの相対ディレクトリ。例の `public` は標準的な候補であり、各リポジトリの実際の配置は個別に確認する。
- `deploy.json` は公開URLやVPS上の絶対パスを指定しない。公開URLの割当と物理配置先の管理はXO側が行う。
- ディレクトリの実在確認、リポジトリ外へのパス逸脱防止、公開URLの重複検出は共通処理側で扱う。
- 公開ベースURLに依存するHTML内の絶対パスについては、相対パスの利用を基本とし、必要に応じて後続仕様で扱う。

JSON Schemaの詳細な制約やXO側のURL割当設定ファイルの形式は後続作業で定義する。このJSONは合意した最小構成を示すもので、現時点では読み取り処理は未実装。

## 判断理由

- 講座が増えてもXO側に講座別のデプロイ実装を増やさずに済むようにするため。
- 公開対象と非公開対象を各リポジトリで明確に分離するため。
- GitHubを正本として、公開内容の更新を単純にし、コピー先との二重管理を避けるため。
- コンテンツの責務と公開基盤の責務を分離するため。
