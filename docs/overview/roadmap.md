## 3. 目指すシステム

Web アプリケーションとして設定画面、メンテナンス画面、認証・認可、データ永続化等を段階的に実装します。ゲームはゲーム開発技術の習得自体を目的とするのではなく、実際に操作できるショーケースとして位置付けます。

将来的には、次のユースケースを想定します。

```text
ゲームを遊ぶ → 欲しいものが生まれる → 購入・決済 → 権利付与 → ゲームへ反映
```

認証、ユーザー管理、商品管理、購入、決済、権利管理、ゲーム等を一つのシステムで連携させます。実課金を必須とせず、仮想決済も選択肢とします。

### 活動の基本理念

本活動の本質的な価値は、個別のプログラミングテクニックや完成品の珍しさではなく、目的とするシステムを成立させるために何を知り、何を判断し、何を行うべきかを理解していることにある。既に有する知識・経験を実際の設計・実装・検証・運用に適用し、その実効性を稼働する成果物と設計判断の記録によって示す。技術習得そのものや、個人開発であることによる驚きを主目的としない。

### 開発目的と模擬実装の境界

商用サービスの運営自体ではなく、具体的な商用サービスを想定した汎用的かつ堅牢なシステムを設計・実装できることの実証を主目的とする。ユーザー管理、商品・購入・決済・権利付与を主要な技術実証対象とする。

- 外部サービスは実在するサービスの契約・制約を想定し、複数のサービスを選択・切替できる設計を追求する。業務処理とサービス固有の接続責務を分離し、差異を隠して同一仕様とみなさない。具体的なサービス名・切替単位・方式は個別設計で決定する。
- 実決済や実顧客情報を扱う商用運用は必須としない。外部接続は模擬実装でもよいが、模擬対象と実装対象を明示し、購入処理のトランザクション管理、権利付与の整合性、認証・認可、入力検証、異常時処理等の内部設計を模擬接続を理由に省略しない。実装範囲は機能ごとに決定する。
- 不具合の発生しにくい設計を目指し、責務・契約・依存関係・信頼境界を明確にする。重複要求、並行処理、通信失敗、結果不明、再試行、部分失敗等の該当するリスクについて、守るべき不変条件、検出・復旧方針、検証条件を個別設計で定める。模擬環境の合格を実サービス接続の合格とみなさない。
- 共通標準 C-005〜C-008、C-101〜C-104、C-201〜C-205、C-301〜C-305、C-401〜C-406、C-1202、C-1306〜C-1307 を関連する設計・検証に適用する。

### ポータルの位置付け

本体ポータルは一般的なゲームアプリのポータルサイトを想定し、利用者が普段使うサービスと同様に自然に利用できるものを目指す。独自性や技術の誇示を目的とせず、システムを成立させる知識の実効性を示す入口とする。ゲーム・アプリは利用動機とショーケースであり主目的ではない。活動目的・世界観・開発実績・勉強会情報はGitHub等の正本を参照できればよく、過剰な宣伝用実装は不要。教材制作は設計・実装・説明能力を示す成果物として位置付ける。本体の本格的ポータルは未実装で、講座共通玄関とは区別する。具体的な画面構成は未確定。開発の優先順は第9節を参照。

## 4. 開発・公開構成

開発環境は Ubuntu / VS Code。GitHub をソースコードとドキュメントの正本とし、VPS 側では原則直接編集しません。

```text
Ubuntu 開発環境
   ↓ Git commit / push
GitHub
   ↓ VPS 側で git pull、サービス再起動等
KAGOYA VPS（Debian）
   ├─ Caddy（HTTPS / Reverse Proxy）
   └─ Express（127.0.0.1:3000、systemd 管理）
       ├─ /api/health、/api/hello
       ├─ /apps/* → src/public/apps
       └─ その他の静的ファイル → src/public
```

公開ドメイン：<https://sarajevo.jp>

次段階の設計：管理者向けは `admin.sarajevo.jp`、独立Express `127.0.0.1:3001` を予定。ソース骨組みとsystemd/Caddyドラフトのみで、**管理者サイトは未公開**。DBはPostgreSQLを候補として論理分離し、将来の物理分離に対応する。

静的講座は `demo.sarajevo.jp` の登録経路でGitチェックアウトの公開専用ディレクトリを直接配信する。共通玄関は `/` のみ。通常更新は `bash deploy/deploy.sh`、Express更新は本体専用手順。GitHub への push だけで自動デプロイされる構成とはしていません。

## 6. 現在のリポジトリ構成（概略）

```text
xo-code-busters/
├── docs/
│   ├── overview/
│   │   ├── roadmap.md
│   │   └── roadmap-changelog.md
│   └── ...
└── src/
    ├── public/   # 静的公開対象（メイン画面、apps/以下の個別アプリ）
    ├── client/   # 旧一般ユーザーモック（静的公開対象外）
    ├── server/        # 既存一般ユーザー Express / API
    ├── admin-client/  # 管理者画面モック
    ├── admin-server/  # 管理者 Express 骨組み（未公開）
    └── shared/        # サーバー側共通ライブラリ骨組み
```

個別アプリは `src/public/apps` に配置し、公開対象を `src/public` に集約しています。

## 7. 公開・セキュリティ方針

既存一般ユーザーExpressの静的配信対象は、`src/public` に限定します。`src/client/mock.html` は非公開の試作ファイルであり、現在のExpress静的配信対象外です。認証・アクセス制御を提供しません。管理者Expressは `/api/health` 以外をHTTP 503とし、管理画面を配信しません。`src/server`、`docs`、`.git`、秘密情報等は直接公開しません。ユーザー入力をファイルパスとして無制限に利用しない等の基本方針を維持し、詳細なセキュリティ設計は機能要件に応じて定義します。

## 9. 今後の開発ロードマップ

2026-11-28確定。一般的なゲームポータルを成立させるための機能群を、依存関係に沿って段階的に実現する。以下は開発の優先順と到達目標であり、個別機能の詳細仕様や技術選定を確定するものではない。

| 段階 | 開発対象 | 到達目標 | 状態 |
|---|---|---|---|
| 1 | ユーザー管理画面モックの完成 | 既存の画面仕様・構成設計・実装を照合し、一般ユーザー・管理者双方のブラウザ操作、主要遷移、入力、仮登録・編集・ログアウトをレビューし、必要な修正と完成判定を行う | 次の作業 |
| 2 | ユーザー管理の本実装 | DB・共通ライブラリの必要部分、認証・認可、登録・ログイン・設定、管理者による検索・編集・停止等を設計・実装し、永続化・アクセス制御・異常系を検証する | 未着手 |
| 3 | 本体ゲームポータルの整備 | 一般的なゲームポータルとしてゲーム選択・起動、会員機能への導線、ログイン後の遷移を統合する。既存ゲーム・アプリを活用し、一般利用者の操作を確認する | 本格実装前 |
| 4 | 商品管理・購入機能 | 商品の管理・表示、購入要求・購入記録の業務契約と状態遷移を設計・実装し、正常系・異常系を検証する | 未着手 |
| 5 | 決済・権利付与・ゲーム連携 | 購入から決済結果、権利付与、ゲーム反映までを一貫して成立させる。外部決済の模擬可否と境界を明示し、重複・部分失敗・結果不明等の整合性を検証する | 未着手 |
| 6 | 全体統合・運用確認 | 一連の利用者・管理者操作、回帰検証、ログ・障害復旧・配備手順を確認し、対象範囲と未確認事項を明示して一つのサービスとして完成判定する | 未着手 |

### 進め方

- 段階1を直ちに次の対象とし、既存成果物を再作成しない。認証・DBの本実装は段階2と区別する。
- 段階2以降の内部実装順序、DB詳細、認証方式、外部サービス名、具体的なゲーム・商品・画面構成は各段階の設計で決定する。商品・購入・決済・権利の契約は相互の整合性を考慮して設計し、段階分けを理由に必要な先行設計を省略しない。
- セキュリティ、テスト、運用、設定・メンテナンス機能、デプロイ整備は必要な段階で並行して実施し、最終段階まで先送りしない。管理者機能はサーバー側認証・認可が完成するまで公開しない。VPSへの配備は明示承認を要する。
- 各段階の開始時に対象・完了条件・検証方法を定め、証跡を残す。既存規約に従い、必要性のない規約改訂や教材制作を独立した先行工程として追加しない。
- 日程・工数は未確定。詳細設計で依存関係や制約が判明した場合は理由を記録してロードマップを更新する。
