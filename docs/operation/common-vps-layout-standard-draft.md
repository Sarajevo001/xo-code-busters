## 追加案：11. 共通VPS配置・公開・永続データ

- **C-1001 適用条件**：本標準を採用し、VPSにGitHubリポジトリを配置するプロジェクト。VPSを使用しないプロジェクトは対象外とし、根拠を記録する。
- **C-1002 リポジトリ配置**：VPS上のGit作業ツリーは原則 `/srv/GitHub/<所有者>/<リポジトリ名>/` に置く。所有者とリポジトリ名はGitHub上の識別子に対応させる。
- **C-1003 ソース構成**：アプリケーション本体は `src/` に配置し、Webから直接配信するGit管理の静的ファイルは `src/public/`、サーバー側実装は `src/server/` に置く。テストコードはルートの `tests/`、設計・仕様・運用文書は `docs/`、デプロイ設定・手順は `deploy/` に置く。用途のないディレクトリの作成は要求しない。
- **C-1004 静的公開とAPIの区別**：Git管理の静的ファイルをWebへ直接公開する場合、公開対象は `src/public/` に限定する。APIなど動的機能はこの静的公開規則の対象外とし、実装を `src/server/` に置き、公開契約・認可を別途定義する。実行時永続データの配信はC-1006に従う。
- **C-1005 公開安全性の検証**：公開URLと対応するファイルシステム範囲を明示し、静的公開対象外の代表的なパス（例: `src/server/`、`docs/`、`tests/`、`deploy/`、`.git/`）を外部から取得できないことを確認する。シンボリックリンクや別名配信経路を含む構成上の公開漏れも確認する。検証対象・期待結果・実測結果を記録する。
- **C-1006 永続データ**：ユーザーアップロード等、アプリケーション実行中に生成・更新される永続データは、原則 `/var/lib/projects/<所有者>/<リポジトリ名>/` 以下に置き、Git管理領域へ保存しない。デプロイは当該領域を削除・初期化・上書きしない。Webからの閲覧が必要な場合は、公開対象・URL経路・必要な認証認可をプロジェクトごとに定義する。一時ファイル、サービス固有の内部状態、ログは用途に応じた別の保存領域を認める。
- **C-1007 書込権限**：Caddyとアプリケーション実行プロセス（Express等）には、`/srv/GitHub/` 以下のGit作業ツリーへの書込権限を与えない。アプリケーションの永続データへの書込権限は `/var/lib/projects/<所有者>/<リポジトリ名>/` 以下の必要な領域に限定して許可する。Caddy固有の内部状態領域は別管理とする。Git更新用のデプロイ主体の権限は別に定義する。
- **C-1008 既存環境移行**：既存プロジェクトも本構成への移行対象とする。ただし稼働環境は、参照パス・Caddy・Express・systemd・デプロイ処理・アクセス権限・公開URL・永続データの影響を評価し、移行順序、事前保全、検証、切り戻し条件を個別計画として定めた後に変更する。他の変更作業との順序を調整する。
- **C-1009 判定と証跡**：対象となるパス、公開設定、実行主体と権限、永続データ保存先、検証結果、移行時の確認結果が対応していれば遵守と判定する。規則違反が確認された場合は違反、実機・設定・検証結果を確認できない場合は判定不能とし、既存のC-002・C-405に従う。

## 影響・留意点

1. 現行XO-Code Bustersは `src/server/server.js` で `src/client/` と `src/apps/` を静的配信している。これらを `src/public/` に集約するには参照URLと静的配信の回帰確認が必要。
2. 現行RPG教材はGit作業ツリーと配信用コピーが分かれている。旧案にある「`/var/www/demo/oop-rpg-workshop` がGit作業ツリー」という記述は実態と一致しないため修正する。
3. Caddy/Expressの書込禁止は実行主体に対する規則であり、デプロイ用Git更新ユーザーまで書込禁止にすると運用不能になる。デプロイ主体を別に定義する。
4. 既存の規約C-001（既存未変更部分への一律遡及を要求しない）と、今回の「既存環境を移行する」という個別決定を混同しない。既存2プロジェクトの移行は別途明示された作業範囲として扱う。
5. `/var/lib/projects/` に置くデータはGitで保護されない。バックアップ・保存期間・容量・アップロード検証は各プロジェクトの設計事項として扱う。
