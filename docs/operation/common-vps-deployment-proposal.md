# 共通VPSデプロイ手順（設計案・未適用）

状態：検討中。既存の `docs/operation/deployment-guide.md` に記載された手動デプロイ方式を置き換えない。GitHub Actions・VPSへの実装、動作確認、運用開始は未実施。

## 1. 目的と範囲
- 複数のGitHubリポジトリについて、既存の「SSH接続後にVPS上で `git pull --ff-only`」という手順をGitHub Actionsから手動起動する。
- 初回適用は静的HTMLを含むプロジェクトで検証する。具体的な対象と値は対象プロジェクト側で管理する。
- GitHubをソースの正本とし、VPS上のソースは直接編集しない。
- Caddy・systemd・Node.jsの設定変更、依存関係更新、サービス再起動は初回の自動化対象外。必要時は既存手順で個別に判断する。

## 2. 共通処理（実装予定）
1. `workflow_dispatch` による明示的な手動起動。実行対象リポジトリ、ブランチ、対象SHA、公開環境を識別する。
2. 対象SHAに対応する既存CIの成功証跡を照合する。未実行・実行中・失敗・SHA不一致・照合不能なら停止する。
3. 許可済みのVPS接続先と作業ディレクトリに限定してSSH接続する。秘密鍵・ホスト情報はGitHub Secrets等で管理し、秘密鍵をGitへ登録しない。SSHホスト鍵は事前に検証して固定する。
4. VPSのGit作業ツリーがクリーンであること、対象ブランチ・remoteが想定どおりであることを確認する。不一致なら停止し、強制resetやmergeは行わない。
5. `git fetch` と対象SHAの照合を行い、`git pull --ff-only` で更新する。pull直前のリモートHEADが対象SHAと異なる場合は停止する。競合時は停止する。
6. 更新後のVPS HEADが対象SHAと一致することを確認する。静的HTMLの公開URLについてHTTP取得を確認し、結果を記録する。HTTP 200のみでは表示・操作の正常性を保証しない。
7. 実行ID、対象SHA、更新前後SHA、対象環境、成功・失敗・判定不能、停止理由を記録する。

## 3. プロジェクト固有設定
共通処理から以下を分離する。
- GitHubリポジトリ、許可ブランチ、CIチェック名・検証方式
- VPS接続先、SSHユーザー、Git作業ディレクトリ
- 公開URL、必要なHTTP確認項目
- 静的ファイル以外の更新がある場合の扱い

任意のパス・任意のシェルコマンドをワークフロー入力として受け付けない。許可された設定のみ使用する。

## 4. 検証計画
目的：既存の手動操作と同等の結果を、手動起動のGitHub Actionsから再現する。
- 成功：承認したSHAがVPSのHEADと一致し、対象HTMLが期待URLで取得でき、既存コンテンツに意図しない変更がない。
- 失敗：CI不合格、SHA不一致、作業ツリー汚染、SSH認証失敗、pull失敗、公開確認失敗。
- 判定不能：CI証跡やVPS状態・HTTP応答を取得できず、更新の成否を確定できない。
- 手順：設定と権限を確認し、読み取り専用の接続・状態確認を行う。その後、ユーザー承認の下、静的HTMLの変更を対象に1回デプロイし、変更前後のSHAと公開内容を比較する。
- 停止条件：前提情報未確定、権限不足、認証・検証失敗、想定外差分、状態不明。無条件の再試行・強制更新をしない。

## 5. 未確定事項（実装前に確認）
- 対象プロジェクトのVPS上のGit作業ディレクトリと、実際の公開ディレクトリの対応。
- GitHub ActionsからのSSH認証手段、VPS側の権限、既存のSSHホスト鍵の検証方法。
- 対象プロジェクトの対象SHAとCI成功を結び付ける具体的なチェック。
- 既存公開URLと最新HTMLの実際の配信状態。
- 共通ワークフローの設置先（管理元の再利用可能ワークフローか各リポジトリ側か）、呼び出し権限。

上記が確定するまで、実行可能なデプロイワークフローを有効化しない。

## 6. 既存手順との関係
`docs/operation/deployment-guide.md` のSSH＋`git pull --ff-only` を基本方式とする。既存の手動手順は引き続き使用可能とし、自動化導入後も復旧・切り分け手段として保持する。

## 7. 個別プロジェクトへの適用
- 対象プロジェクトのリポジトリ内に環境固有の設定と確認結果を記録する。
- 共通手順書には具体的な配置先パス・公開URLを記載しない。
- 設定が未確定または検証できない場合、デプロイを有効化しない。

## 8. 共通標準v1.4.0との関係（CHG-000012）
- 共通標準v1.4.0は管理元 `main` に正式反映済み。規約本文の採用とVPS実環境の移行・GitHub Actions導入は別工程とする。
- 現行XO-Code BustersのGit作業ツリーは既存記録上 `/srv/xo-code-busters`。移行先は `/srv/GitHub/Sarajevo001/xo-code-busters`。RPG教材の既存Git作業ツリーは `/home/debian/oop-rpg-workshop`、旧静的公開コピーは `/var/www/demo/oop-rpg-workshop`、移行先Git作業ツリーは `/srv/GitHub/Sarajevo001/oop-rpg-workshop`。
- 共通手順の作業ディレクトリは、移行前後で**実機検証済みの許可パス**に固定する。旧パスを無条件に自動化したり、移行完了前に新パスを有効化したりしない。
- `src/public/` への静的公開範囲変更、Caddy/systemd設定変更、データ移動、権限変更は初回GitHub Actions導入の範囲外。既存URLの維持と切り戻しを個別移行計画で検証する。
- 公開URLを保持し、管理画面など未認証の非公開領域を静的公開ルートへ混入させない。実行主体のGit領域書込禁止と永続データ領域の権限分離は移行検証で扱う。
- VPSへのSSH接続・実機設定の取得は現時点で実施していない。稼働状態を確認済みとは扱わない。
